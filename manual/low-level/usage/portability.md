# Portability

In an ideal world, bindings could be generated by `hs-bindgen` once on one
platform[^1] and compiled and/or run on another. Then the generated bindings
would be maximally portable. However, bindings generated by `hs-bindgen` are not
portable in general (indeed, it will be rare that they are). The slogan to
remember is:

> The bindings generated by `hs-bindgen` should be regarded as build artifacts.

In this manual section, we aim to answer three questions:

* [Causes][t:causes]: what causes non-portable bindings?
* [Consequences][t:consequences]: how does non-portability materialize in
  generated bindings?
* [Solutions and mitigations][t:solutions]: how do we mitigate or solve
  non-portability of generated bindings?

This manual section is not necessarily exhaustive. If you experience portability
issues that are not (satisfactorily) described here, please let us know by
creating an issue on the [issue tracker][github:issue-tracker].

There are ongoing efforts to improve portability: see [issue #1746][issue-1746].
[Cross-compilation][manual:cross-compilation] may also be useful when one needs
to generate bindings for one specific platform, but this does not solve the
portability problem by itself.

## Preliminary: reasonably designed C libraries

In theory, the public API of a C library may vary wildly based on the platform,
specially since [conditional compilation][t:conditional-compilation] can almost
arbitrarily modify C source code. *Unreasonably designed* C libraries are
therefore likely not portable (or even very useful). We should not expect to
generate portable bindings for such libraries, or to have sensible guidelines
for solving/mitigating non-portable bindings. Throughout this manual section, we
expect C libraries to be *reasonably designed* with at least some degree of
portability in mind.

## Causes
[t:causes]: #causes

`hs-bindgen` relies on `libclang` for all decisions, such as the [resolution of
C preprocessor (CPP) conditionals][t:conditional-compilation]. This means that
the shape of the generated bindings and the corresponding binding specifications
depends on the platform where `hs-bindgen` runs. In general, this causes
generated bindings to be non-portable across platforms, or even different
configurations of the same library.

What are the different reasons that `libclang` could report platform-dependent
information?

### Compiler decisions

The C reference specifies, amongst other things, the C language and standard
libraries, but leaves it up to an implementation to decide on many of the
details, for example:

* What is the size of an `int`?
* Is the `char` type signed?
* How much unnamed padding should be included between struct fields?
* How should adjacent bit-fields be packed?
* How is `size_t` implemented?

These compiler decisions may be platform-dependent. For example, a compiler
implementation may decide on one platform that an `int` is 32 bits, and 64 bits
on another. If the size of an `int` is used in the generated bindings, then the
bindings will differ depending on the platform.

In some cases `libclang` may even disagree with other C compilers on some
information, though `clang` strives to be [compatible][clang:compatibility] with
other C compilers. This is relevant for Haskell bindings as well: `hs-bindgen`
uses `libclang` to generate bindings, `ghc` uses `clang` or `gcc` to compile
Haskell bindings, and (external) C libraries could be compiled with the same or
another C compiler. We have yet to find examples where discrepancies between
compilers have been a problem, however.

## Conditional compilation
[t:conditional-compilation]: #conditional-compilation

Conditional compilation uses CPP conditionals to arbitrarily modify C
declarations, or even leave them out entirely. Some conditional compilation
happens without user intervention, for example as part of the standard libraries
implementation. It can also be intended to be explicitly configured by the user.
`libclang` resolves these CPP conditionals before `hs-bindgen` gets to traverse
them, so `hs-bindgen` cannot detect the difference between alternatives.

For example, consider a header that uses `#ifdef` to vary a struct's layout:

```c
typedef struct {
    int type;
#ifdef USE_EXTENDED
    double extra;
#endif
    int value;
} my_record;
```

When `hs-bindgen` processes this header with `USE_EXTENDED` defined, the
generated struct will have three fields (`type`, `extra`, `value`). Without it,
the struct will have only two (`type`, `value`). The generated bindings will
differ accordingly.

## Configure-generated headers
[t:configure-headers]: #configure-generated-headers

A more subtle case arises with libraries whose public headers are generated by
`./configure`, CMake, or similar build systems. These tools probe the host
system and inject `#define`s that silently affect the public API.

For example, a library might generate a `config.h` that is included transitively
by the public headers:

```c
/* generated by ./configure */
#define HAVE_IPV6 1
#define SIZEOF_LONG 8
```

Nothing in the public header itself signals that it is platform-specific, and
`hs-bindgen` has no way to distinguish configure-generated content from
hand-written content. The generated bindings will simply reflect whichever
`#define`s were in effect at the time.

## Consequences
[t:consequences]: #consequences

Generated bindings can be platform-dependent because `libclang` makes
platform-dependent decisions.

What are some common ways in which non-portability materializes in generated
bindings?

### Memory layout of types
[t:memory-layout]: #memory-layout-of-types

C types such as structs and unions have a memory layout that is
platform-dependent. The memory layout includes information about the type and
its fields, such as size, alignment, offset, and (bit-)width. `hs-bindgen`
generates bindings that hard-code these values, for example to implement class
instances like `Storable`, `HasCField`, `HasCBitField`, and `HasField` (for
union bit-fields). As such, bindings generated on one platform may not hard-code
the right values for a different platform.

### Functions and FFI types
[t:ffi-types]: #functions-and-ffi-types

For C, functions `hs-bindgen` generates bindings in the form of Haskell
functions. While the *public* function binding may look portable, the
*implementation* of that binding is most probably not portable. The
implementation uses a `foreign import` declaration that only references a small
set of "FFI types". These FFI types are very rarely portable.

For example, a C function may use an `int` argument, the public binding may use
`CInt`, but the binding implementation may use `Int32` or `Int64` depending on
the platform the bindings are generated on.

The precise reason why we use FFI types in function binding implementations is
quite technical, but chiefly it ensures that the bindings that `hs-bindgen`
generates are *compositional*. See the "Full example" dropdown below for a
detailed explanation.

## Solutions and mitigations
[t:solutions]: #solutions-and-mitigations

There are several strategies for managing non-portable bindings. In some cases,
portability may be improved by user intervention.

### Define macros explicitly

State the macros the headers expect as `#define` root directives, so that the
CPP resolution matches the intended target:

* `hs-bindgen-cli preprocess --hash-define USE_EXTENDED 1 ... foo.h`
* `hashDefine "USE_EXTENDED" "1"` in Template Haskell

A root directive is stated once and reaches every C stage: both the headers
`libclang` parses and the generated C wrapper source that GHC compiles. This
matters, because a header parsed under one set of macros and compiled under
another gives missing symbols or, worse, silently mismatched `struct` layouts.
Note that a `-D` passed via `--clang-option` or `BINDGEN_EXTRA_CLANG_ARGS` does
*not* have this property: it affects binding generation alone. See [C
stages][manual:c-stages].

Macros that select an *implementation*, as in a header-only library, are the
exception: they must be confined to a single translation unit. See [Header-only
libraries][manual:c-stages-header-only].

### Treat binding generation as part of the build process

Do not assume that generated binding are portable across platforms. On each
target platform, regenerate the bindings using that platform's headers and
configuration (perhaps using `SetupHooks`). At present `hs-bindgen` does not yet
provide any explicit support for making this process easier.

### Gate platform-specific packages

If distributing generated bindings (e.g. on Hackage), gate them to the
platform(s) they were generated on (or
[cross-compiled][manual:cross-compilation] for). For example, in a `.cabal`
file:

```cabal
if !(os(linux) && arch(x86_64))
  buildable: false
```

See [Installation][manual:installation] for further discussion of
platform-specific considerations.

The [`bundled-c` example][example:bundled-c] provides a concrete demonstration.
Its C header uses `#ifdef RECT_3D` to optionally add a struct field; The
`test-cpp-mismatch.sh` script exercises the most subtle case: bindings are
generated *without* the flag but the C code is compiled *with* it, causing
silent runtime data corruption.

[t:portable-types]: #use-portable-types

See the [Portable types][manual:portable-types] manual section.
