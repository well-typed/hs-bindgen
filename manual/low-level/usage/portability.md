# Portability

In an ideal world, bindings could be generated by `hs-bindgen` once on one
platform[^1] and compiled and/or run on another. Then the generated bindings
would be maximally portable.

Bindings generated by `hs-bindgen` are not portable in general, and _cannot_ be,
as we shall see in [Why bindings are non-portable in general][t:why]. Therefore,
`hs-bindgen` should be part of your project's build process:

> The bindings generated by `hs-bindgen` should be regarded as build artifacts.

This makes portability a non-issue because bindings will always be generated for
the specific system that the build runs on. Schematically, it looks something
like this:

```
           compilation
      (hs-bindgen, ghc, gcc)
*.h  -----------------------> *.hs (generated bindings)
*.hs                          *.hi
*.c                           *.o
```

This can be achieved, for example, by:

* Running `hs-bindgen` through an external build system, such as Make, Nix,
  or similar tools.
* Running `hs-bindgen` through [Cabal hooks][wt:cabal-hooks].
* Using the [Literate Haskell mode][manual:invocation-lhs].
* Using the [Template Haskell mode][manual:invocation-th].

That said, in some cases we do not have to accept that the bindings are
non-portable. For _specific_ headers, and with user input, portable bindings are
sometimes possible, so that binding generation can be separated from
compilation:

```
      generation                            compilation
     (hs-bindgen)                            (ghc, gcc)
*.h -------------> *.hs generated bindings ------------> *.hi
                   *.hs Haskell sources                  *.o
                   *.c C sources
```

We will describe some approaches in section [Improving
portability][t:improving], but the main idea is to limit the generated bindings
to those that can be portable, possibly assisted by a separate compile-time
step (for example using the C preprocessor or `hsc2hs`).

One extreme version of this is to generate multiple bindings for different
platforms, and pick a suitable set at compilation time. This approach has
limited use, however, because the number of bindings we can generate a priori is
finite.

This manual section is not necessarily exhaustive. If you experience portability
issues that are not (satisfactorily) described here, please let us know by
creating an issue on the [issue tracker][github:issue-tracker].

## Why bindings are non-portable in general
[t:why]: #why-bindings-are-non-portable-in-general

Let's start with an example to describe why bindings are non-portable in
general. We have a header with a struct `S` with two fields, like so:

```c
struct S {
  int x;
  char y;
};
```

`hs-bindgen` generates bindings for `S` that could look roughly like so on one
platform (we simplified the bindings and omitted irrelevant details):

```hs
data S = S
  { x :: CInt
  , y :: CChar
  }

instance Storable S where
  sizeOf _ = 8
  peek ptr = do
    x <- peek ptr
    y <- peek (ptr `plusPtr` 4)
    pure (S x y)
  -- .. more stuff ..
```

`hs-bindgen` uses `libclang` to parse C header files into an AST that is
labelled with information, such as memory layout, and converts that AST into
bindings. In the example above, we can see that `libclang` told us, amongst
other things, that the offset of field `y` is 4, but it may decide on a
different offset on a different platform. The C standard specifies the C
language and standard libraries, but leaves it up to an implementation to decide
on many of the details, for example:

* What is the size of an `int`?
* Is the `char` type signed?
* How much padding should be included between struct fields?

In practice these decisions are largely platform-dependent (including C
compiler-dependent). For example, the size of an `int` often depends on the
machine's word size. So, `libclang` might assign a different offset to `y` based
on the platform, which leads to different bindings, and hence non-portability.
We call this *inherent* non-portability.

In some cases `libclang` may even disagree with other C compilers on some
information, though `clang` strives to be [compatible][clang:compatibility] with
other C compilers, most importantly `gcc`. This is relevant for Haskell bindings
as well: `hs-bindgen` uses `libclang` to generate bindings, `ghc` uses a C
compiler (typically `gcc` or `clang`) to compile the C wrappers that
`hs-bindgen` generates, and the C library itself may have been compiled with yet
another compiler. That said, we have yet to find examples where discrepancies
between `clang` and `gcc` have been a problem.

Non-portability may also be *user-induced* when CPP is used, in which case C
declarations can be arbitrarily modified. `libclang` resolves CPP before
`hs-bindgen` gets its hands on the parsed AST, so `hs-bindgen` only sees the
preprocessed file.

CPP may be used for conditional compilation. Let's say `S` had been implemented
like so instead:

```c
#ifdef C
#define T int
#else
#define T long long int
#endif
struct S {
  T x;
  char y;
};
```

`y` would (probably) be assigned a different offset based on whether `C` is
defined or not. More importantly, the type of the Haskell field `x` may change
from `CInt` to `CLLong` depending on whether `C` is defined.

Similarly, CPP may also be used in libraries that use headers that are generated
by `./configure`, CMake, or similar build systems. These tools probe the host
system and inject `#define`s that mold the public API. In general, `hs-bindgen`
can't distinguish between configure-generated content and "fixed" content. For
example, a library might generate a `config.h` that is included by the public
header `lib.h`, where the contents of `config.h` are different based on whether
the configure script runs on some platform `A` or platform `B`:

```c
// config.h: generated by ./configure on platform A
#define T int

// config.h: generated by ./configure on platform B
#define T long long int

// lib.h: written by hand
#include "config.h"
struct S {
  T x;
  char y;
};
```

In addition to inherent non-portability and user-induced non-portability, we
have a third source too: `hs-bindgen` itself. For example, if we need a
`Storable` instance for `S`, we need its layout: inherent non-portability. But
if `S` is only ever used by pointer, nothing requires the layout, yet by default
`hs-bindgen` still generates the instance. That is *`hs-bindgen`-induced
non-portability*.

In summary, we distinguish three sources of non-portability:

* inherent: the platform determines details such as memory layout
* user-induced: CPP may arbitrarily alter the header file
* `hs-bindgen`-induced: `hs-bindgen` unnecessarily exposes platform details

Often no single source is to blame, and non-portability arises from the
interplay of all three.

## Improving portability
[t:improving]: #improving-portability

At its core, the answer to "how to avoid non-portability in bindings" is simply:
don't use `hs-bindgen` to generate the problematic bindings. For the simplest
cases that might suffice: for the example of unnecessary instances from the
previous section, a [prescriptive binding specification][manual:prescriptive]
can be used to omit `Storable` and other layout-dependent instances. At a
slightly coarser granularity, [selection
predicates][manual:selection-predicates] can be used to skip entire C
declarations.

In many cases, however, the now missing generated bindings need to be replaced,
which will require user input. In this section we will describe a number of ways
in which this can be done.

### Inherent non-portability: platform-dependent types

Portability can be greatly improved by using types with a platform-dependent
implementation. The standard `base` package includes many examples of these; for
example, it defines `CSize` using CPP roughly as

```hs
#include "HsBaseConfig.h"  -- generated by configure

newtype CSize = CSize HTYPE_SIZE_T
```

Another way to do this is to apply the "use `hs-bindgen` to generate multiple
sets of bindings" idea from the introduction, but at a much smaller granularity:
generate multiple bindings for a single type, and then use CPP to choose between
them. Yet another option is to use other tools, such as `hsc2hs`, to fill in
platform-dependent details.

Whatever the approach, this amounts to _splitting_ binding generation across
the two steps:

```
      generation                                compilation
     (hs-bindgen)                           (hsc2hs, cpp, ghc)
*.h -------------> *.hs generated bindings -------------------> *.hi
                   *.hs Haskell sources                         *.o
                   *.c C sources
```

> [!NOTE]
> It might be worth exploring whether `hs-bindgen` _itself_ could generate
> such "split generation" bindings; see for example
> [#1818](https://github.com/well-typed/hs-bindgen/issues/1818) and
> [#2294](https://github.com/well-typed/hs-bindgen/issues/2294).
> Indeed, [`c2hsc`][hackage:c2hsc], an older alternative to `hs-bindgen`,
> automatically generates `.hsc` files. It is important to note, however, that
> this cannot resolve _all_ sources of non-portability.

Whatever method is used to design a platform-dependent type, `hs-bindgen` then
needs to be told about it [through an external binding
specification][manual:substituting]. The [binding specification for the C
standard library][manual:stdlib-spec] that ships with `hs-bindgen` (and is
enabled by default) is an example, and includes a specification for `CSize`.

### `hs-bindgen`-induced non-portability: FFI types

Let's continue the `CSize` example from the previous section, and let's assume
that `CSize` is given a bespoke platform-dependent implementation. Unless told
otherwise, `hs-bindgen` will still not refer to `CSize` when it appears in
function signatures such as

```c
size_t strlen(const char *s);
```

Instead, it will use the underlying type:

```hs
foreign import ... "strlen" strlen_wrapper :: PtrConst CChar -> IO CULong

strlen :: PtrConst CChar -> IO CSize
strlen = ... strlen_wrapper ...
```

This is `hs-bindgen`-induced non-portability: the foreign import unnecessarily
exposes platform details (on _this_ machine `size_t` expands to `CULong`), even
though ultimately this is to work around `ghc` limitations; see [the discussion
of FFI types][manual:ffi-types] for a detailed explanation.

The fix is to explicitly tell `hs-bindgen` what type to use in foreign imports;
this amounts to an entry in the external binding specificaiton such as

```yaml
- hsname: CSize
  representation:
    newtype:
      ffitype:
        hsmodule: Foreign.C
        hsname: CSize
```

`CSize` must then also be given a corresponding `HasFFIType` instance:

```hs
instance HasFFIType CSize where
  type FFIType CSize = CSize

  toFFIType   = id
  fromFFIType = id
```

Once done, the `foreign import` will read

```hs
foreign import ... "strlen" strlen_wrapper :: PtrConst CChar -> IO CSize
```

The default binding specification for the standard library does exactly this.

### User-induced non-portability: hand-written unifying interface

In general, user-induced non-portability can take any shape at all; types might
exist on one platform but not another, function signatures might be completely
different on different platforms, etc. Automatic tooling can only be of limited
assistance here, but users who understand the headers well can hand-write
bindings for the parts of the library that need it:

```hs
module Handwritten (publicFunction) where

#if PLATFORM1

data TypeThatExistsOnlyHere

foreign import .. weirdFunction :: ...

publicFunction :: ...
publicFunction = .. use TypeThatExistsOnlyHere and weirdFunction ..

#elif PLATFORM2

..

publicFunction :: .. same signature as for PLATFORM1..
publicFunction = .. but with a different implementation ..

#endif
```

Then `hs-bindgen` can still be used to generate bindings for the rest of the
library, perhaps assisted by [external binding specs for hand-written
types][manual:substituting].

In some cases the unifying interface already _exists_, with the C standard
library as the most notable case in point. For example, the standard mandates
that `struct tm` _must_ have certain fields, but in an actual implementation it
_may_ have additional fields. `CTm`, the implementation of `struct tm` in the
`hs-bindgen` runtime, therefore defines only the standard fields, omitting any
non-standard ones. This is facilitated by the fact that `hs-bindgen-runtime`
splits the functionality of `Storable` into three separate classes:
`StaticSize`, `ReadRaw` and `WriteRaw`. For `CTm`, instances for `ReadRaw` and
`StaticSize` are available, but not for `WriteRaw`, as we'd have no way to
populate the non-standard fields. `CTm` itself is defined using `hsc2hs`.
