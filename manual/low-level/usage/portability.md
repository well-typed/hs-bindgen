# Portability

In an ideal world, bindings could be generated by `hs-bindgen` once on one
platform[^1] and compiled and/or run on another. Then the generated bindings
would be maximally portable. However, bindings generated by `hs-bindgen` are not
portable in general. The slogan to remember is:

> The bindings generated by `hs-bindgen` should be regarded as build artifacts.

If bindings are generated *as part of the build process*, then portability is a
non-issue because bindings will always be generated for the specific system that
the build runs on. This can be achieved, for example, by:

* Running `hs-bindgen` through an external build system, such as as Make, Nix,
  or similar tools.
* Running `hs-bindgen` through [Cabal Hooks][wt:cabal-hooks].
* Using the [Literate Haskell mode][manual:invocation-lhs].
* Using the [Template Haskell mode][manual:invocation-th].

It's also possible to generate multiple bindings for different platforms *a
priori*, as long as the *build process* ensures that the bindings are suitable
for the platform that they are built on. This can be achieved using conditionals
in the Cabal file, or Cabal hooks, or an external build system, etc. This
approach has limited use, however, because the number of bindings we can
generate a priori is *finite*.

Finally, we *can* generate portable bindings that need not be build artifacts,
but this requires user input. However, it is important to first understand [why
bindings are non-portable in general][t:why] before we can discuss
[solutions][t:solutions].

This manual section is not necessarily exhaustive. If you experience portability
issues that are not (satisfactorily) described here, please let us know by
creating an issue on the [issue tracker][github:issue-tracker].

## Why bindings are non-portable in general
[t:why]: #why-bindings-are-non-portable-in-general

Let's start with an example to describe why bindings are non-portable in
general. We have a header with a struct `S` with two fields, like so:

```c
struct S {
  int x;
  char y;
};
```

`hs-bindgen` generates bindings for `S` that could look roughly like so on one
platform (we simplified the bindings and omitted irrelevant details):

```hs
data S = S
  { x :: CInt
  , y :: CChar
  }

instance Storable S where
  sizeOf _ = 8
  alignment _ = 4
  peek ptr = do
    x <- peek ptr
    y <- peek (ptr `plusPtr` 4)
    pure (S x y)
  poke ptr S{x, y} = do
      poke ptr x
      poke (ptr `plusPtr` 4) y
```

`hs-bindgen` uses `libclang` to parse C header files into an AST that is
labelled with information, such as memory layout, and converts that AST into
bindings. In the example above, we can see that `libclang` told us, amongst
other things, that the offset of field `y` is 4, but it may decide on a
different offset on a different platform. The C reference specifies the C
language and standard libraries, but leaves it up to an implementation to decide
on many of the details, for example:

* What is the size of an `int`?
* Is the `char` type signed?
* How much unnamed padding should be included between struct fields?

In practice these decision are largely platform-dependent (including C
compiler-dependent). For example, the size of an `int` often depends on the
machine's word size. So, `libclang` might assign a different offset to `y` based
on the platform, which leads to different bindings, ergo, we have
non-portability. We call this *`clang`-induced* non-portability.

In some cases `libclang` may even disagree with other C compilers on some
information, though `clang` strives to be [compatible][clang:compatibility] with
other C compilers, most importantly `gcc`. This is relevant for Haskell bindings
as well: `hs-bindgen` uses `libclang` to generate bindings, `ghc` indirectly
uses `clang` or `gcc` to compile Haskell bindings, and (external) C libraries
could be compiled with the same or another C compiler. We have yet to find
examples where discrepancies between `clang` and `gcc` have been a problem,
however.

Non-portability may also be *user-induced* when CPP is used, in which case C
declarations can be arbitrarily modified. `libclang` resolves CPP before
`hs-bindgen` gets its hands on the parsed AST, so `hs-bindgen` only sees the
preprocessed file. `libclang` is in charge of resolving CPP conditionals, so you
may argue that we should call it `clang`-induced non-portability as well.

CPP may be used for conditional compilation. Let's say `S` had been implemented
like so instead:

```c
#ifdef C
#define T int
#else
#define T long long int
#endif
struct S {
  T x;
  char y;
};
```

`y` would (probably) be assigned a different offset based on whether `C` is
defined or not. But maybe more importantly, the type of the Haskell field `x`
may change from `CInt` to `CULong` depending on whether `C` is defined.

Similarly, CPP may also be used in libraries that use headers that are generated
by `./configure`, CMake, or similar build systems. These tools probe the host
system and inject `#define`s that silently affect the public API. In general,
`hs-bindgen` can't distinguish between configure-generated content and "fixed"
content. For example, a library might generate a `config.h` that is included by
the public header `lib.h`, where the contents of `config.h` are different based
on whether the configure script runs on some platform `A` or platform `B`:

```c
// config.h: generated by ./configure on platform A
#define T int

// config.h: generated by ./configure on platform B
#define T long long int

// lib.h: written by hand
#include "config.h"
struct S {
  T x;
  char y;
};
```

Arguably, not just the two sources of non-portability we have discussed so far
can be assigned blame for non-portability, but `hs-bindgen` too. The example C
header files we have seen do not themselves expose the memory layout of `S`
directly -- it can still be queried using C macros like `offsetof` and `sizeof`
from outside the headers -- but `hs-bindgen` decided to hard-code the offset of
`y` into the Haskell bindings. In such cases, the non-portability is also called
*`hs-bindgen`-induced* non-portability.

Moreover, the three sources can often not be assigned individual blame for
non-portability. It is often caused by an interplay between the three sources.

In summary, we distinguish three sources of non-portability:

* `clang`-induced: `libclang` makes platform-dependent
  decisions, such as memory layout
* `hs-bindgen`-induced: `hs-bindgen` decides to expose choices that `libclang`
  made
* user-induced: CPP may arbitrarily alter the header file

## Portable types

Portability can be greatly improved by using portable types: types that have a
platform-dependent implementation. Even types like `CSize` fall into this
category.

## Use stdlib external binding specification

`hs-bindgen` comes with a builtin external binding specification for the C
standard library, which maps standard C types to portable types. It is
recommended to use this.

## Abstraction
[t:abstraction]: #abstraction

In some cases, we might not need the full feature set for a generated binding.
For example, if a struct is only ever referenced by pointer, we don't need
`Storable`-related instances. `hs-bindgen` can be instructed not to generate
such instances, for example using prescriptive binding specifications. This
makes the generated type "more portable".

solved by this unless you omit all these instances as well.

## FFI types
[t:ffi-types]: #ffi-types

When types are intended to be used in `foreign import`s, we use their FFI type
instead. FFI types may be platform-dependent. Assign portable FFI types manually
instead.

## Manual bindings

When CPP is used, declarations can be modified arbitrarily, so all bets are off
for `hs-bindgen` to generate portable bindings without user input. Still, the
user might understand how the CPP works. In such cases, the user could
surgically write (parts) of bindings by hand, and use them as inputs/external
types for generating the remainder of the bindings.
