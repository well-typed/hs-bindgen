# FFI types

Compositionality of generated bindings is achieved through the use of [external
binding specifications][manual:binding-specifications]. They allow generated
bindings to use types imported from another module. In the past, we experienced
that using such *external types* in `foreign import` declarations could lead to
code that failed to compile (see [issue #1282][issue-1282]) due to an
unfortunate quirk of how `foreign import`s work with `newtype`s in `ghc`. This
behaviour was easy to elicit with external binding specifications that are
written by hand, but more importantly the problem could even occur when we would
only use external binding specifications that were generated by `hs-bindgen`.
The compositionality of generated bindings would be severely limited by this,
and so the solution we implemented is to only use a small set of *FFI types* in
`foreign import` declarations. This ensures that `hs-bindgen` always generates
compositional bindings *by default*, though it is still possible to generate bad
code with manually written external binding specifications.

FFI types are used anytime that `hs-bindgen` would generate a `foreign import`
declaration. However, the rationale behind using FFI types is the same
regardless of the type of binding, so we will focus only on functions in this
manual section. For completeness, here is a list of bindings that use `foreign
import` declarations -- and therefore use FFI types -- in their implementation:

* Bindings for C functions
* Bindings for C global variables
* Bindings for [C function types involving **domain-specific
  types**][manual:functions-tofromfunptr].

In this manual section, we will describe how bindings are generated so that they
are compositional.

* In the [The compositionality problem][t:the-compositionality-problem] sub-section,
  we will illustrate that the compositionaly problem arises when using
  *non-transparent* `newtype`s in foreign import declarations. We will also show
  that two proposed solutions are not satisfactory:

  1. Forcing module exports can not solve the problem in general due to name
    conflicts.
  2. Forcing module imports is not desirable due to messy dependency management.

* In the [`HasFFIType`][t:the-hasffitype-class] sub-section, we explain our
  actual solution to the compositionality problem, where we only use *FFI types*
  -- a set of types that is similar to foreign types, but without `newtype`s --
  in `foreign import` declarations. We will also explain the `HasFFIType` class
  hierarchy that is used to convert types to FFI types and back, which allows us
  to preserve useful type signatures (e.g., involving `newtypes`). Finally, some
  caveats apply to this solution that users should be aware of, and they are
  described as well.

* In the [Portability][t:portability] sub-section, we discuss that FFI types
  cause bindings to be non-portable *in general*. We show a brief example of a
  function binding as it would currently be generated, highlighting how the type
  of that function binding looks portable and how the *implementation* is not
  because FFI types are platform-dependent.

## The compositionality problem
[t:the-compositionality-problem]: #the-compositionality-problem

Suppose we have a C header `our_lib.h` with a function `g` that we want to
generate bindings for. `g` uses a type `Foo` from another library
`some_other_lib.h`:

```c
// some_other_lib.h
typedef int Foo;

// our_lib.h
#include <some_other_lib.h>
int g(Foo x);
```

We have an external binding specification that maps `Foo` to some type `CFoo` in
some Haskell library somewhere. With these inputs, `hs-bindgen` would have
generated bindings in the past that looked roughly like so:

```hs
module OurLib where

import SomeOtherLib qualified

foreign import ccall safe "g" g :: SomeOtherLib.CFoo -> IO CInt
```

`g` may fail to compile depending on how `CFoo` is implemented.

For `ghc` to compile `g`, it must be able to determine whether the type of `g`
is a valid *foreign type*. Foreign types are defined in [Section 8.4.2 of the
Haskell 2010 Language Report][haskell2010:ffi-foreign-types].[^2] Broadly,
foreign types are function types that (may) end in `IO`, where each argument and
result type is a marshallable type such as `Int`, `Word64`, or `Ptr a`. `data`
types are never allowed, but `newtype`s are allowed as long as `ghc` can
determine that they are `Coercible` to a valid foreign type.[^3]

Going back to the example, in order to determine whether a newtype `CFoo` is a
foreign type, the constructor for `CFoo` *and the constructors for anything
`CFoo` depends on itself* must be in scope. In other words, `CFoo` should be
*transparent* all the way down. This is the source of the compositionality
problem: it is hard to ensure *in general* that a newtype `CFoo` is transparent
when generating bindings.

Let's say `CFoo` is defined as follows:

```hs
newtype CFoo = CFoo CInt
```

In this case, `CFoo` is valid foreign type. Importing `SomeOtherLib` brings the
constructor for `CFoo` in scope, and `CInt` is a valid foreign type as long as
its constructor is imported -- which is always true for generated bindings.[^4]

Now let's say that `CFoo` is defined as follows instead:

```hs
newtype CFoo = CFoo CBar
```

Assuming `CBar` is defined in some other module, `g` no longer compiles unless
we somehow also import the module that defines `CBar`, even though `CBar` could
be an implementation detail of `CFoo`.

For a while we could resolve this by insisting that if you have a type intended
for use in FFI like this, you must also re-export the constructors for
everything that the type depends on. Unfortunately, that does not work if there
are name clashes, for example:

```hs
newtype CFoo = CFoo SomeInternalModule.CFoo
```

Haskell does not allow exporting multiple *different* types with the same name
from the same module -- not even if the types have a unique qualified name.

We also considered extending binding specifications to record "additional
required imports". Though this would work, it would be messy. An external
binding specication for a module in one Haskell package might refer to *other*
packages. As a result, users would have to declare more packages in their cabal
`build-depends` field. And in Template Haskell mode, `hs-bindgen` cannot
generate additional imports, so users would have to add those by hand.

In the end, we decided that neither forcing exports or forcing imports was a
desirable solution, so we set out to find a new solution. This became the
 `HasFFIType` class that is described in the next sub-section.

## The `HasFFIType` class
[t:the-hasffitype-class]: #the-hasffitype-class

`newtype`s are the source of the compositionality problem, so eliminating them
from `foreign import` declarations fixes the problem. This is the solution that
`hs-bindgen` implements. Generated `foreign` import declarations only use *FFI
types*[^5]: a set of types that is similar to foreign types, but without
`newtype`s. We still generate a *public function binding* -- a separate Haskell
function -- with more useful types such as `newtype`s. The public function
bindings converts the function arguments to their FFI types before invoking the
`foreign import` declaration, and the function result is mapped from its FFI
type back to its actual type.

We have a class `HasFFIType` in `hs-bindgen-runtime`, which maps any type to its
FFI type, along with conversions. The class roughly looks like this:

```hs
class HasFFIType a where
  type FFIType a :: Type
  toFFIType :: a -> FFIType a
  fromFFIType :: FFIType a -> a
```

Though fitting in spirit, this is a simplification of the actual class
definition. In reality, `FFIType a` is only allowed to map to a fixed set of FFI
types, and we achieve this using some type trickery that we have chosen to omit
here because it distracts from the general idea.

`HasFFIType` instances can currently only be derived using `newtype`-deriving to
prevent mistakes in defining the mappings between types and their FFI types.

> [!NOTE]
>
> There are plans to allow users to define their own instances with arbitrary
> mappings in the future. See [issue #1565][issue-1565].

The set of FFI types is defined using this grammar:

```math
\begin{align*}
  FFIType & \rightarrow & & FFIType ~ \texttt{->} ~ FFIType \\
  ~       & |           & & \texttt{()}                     \\
  ~       & |           & & \texttt{IO} ~ FFIType           \\
  ~       & |           & & \texttt{Int}                    \\
  ~       & |           & & \texttt{Double}                 \\
  ~       & |           & & \texttt{Float}                  \\
  ~       & |           & & \texttt{Bool}                   \\
  ~       & |           & & \texttt{Int8}                   \\
  ~       & |           & & \texttt{Int16}                  \\
  ~       & |           & & \texttt{Int32}                  \\
  ~       & |           & & \texttt{Int64}                  \\
  ~       & |           & & \texttt{Word}                   \\
  ~       & |           & & \texttt{Word8}                  \\
  ~       & |           & & \texttt{Word16}                 \\
  ~       & |           & & \texttt{Word32}                 \\
  ~       & |           & & \texttt{Word64}                 \\
  ~       & |           & & \texttt{Ptr Void}               \\
  ~       & |           & & \texttt{FunPtr Void}            \\
  ~       & |           & & \texttt{StablePtr Void}         \\
\end{align*}
```

FFI types closely resemble [foreign types][haskell2010:ffi-foreign-types]
without newtypes. One might expect that FFI types are a subset of foreign types,
but that is not the case. For example, `() -> IO ()` is an FFI type, but it is
not a foreign type because `()` is not allowed in a function argument position.
This is not a problem in practice, because `hs-bindgen` currently never uses
such "invalid" FFI types in `foreign import` declarations.

> [!NOTE]
>
> There are plans to revisit the `HasFFIType` class hierarchy in the future,
> which may get rid of FFI types that are not also valid foreign types. See
> [issue #1745][issue-1745].

Note also that types from `Foreign.C.Types`, such as `CInt`, are not considered
FFI types because they are themselves `newtype`s. Moreover, note that FFI types
only include `Void` pointer types. The pointed-to type is not actually relevant
for `foreign import` declarations, so we only use `Void` as a simplification.

Going back to the `CFoo` example from the previous sub-section ([The
compatibility problem][t:the-compositionality-problem]), its instance may look
like so:

```hs
instance HasFFIType CFoo where
  type FFIType CFoo = FFIType CInt
  toFFIType (CFoo x) = toFFIType x
  fromFFIType x = CFoo (fromFFIType x)
```

`HasFFIType` instances are composable, meaning that the `HasFFIType` instance
for `CFoo` can defer to the the `HasFFIType` instance for `CInt`.

Now, if we want to use `CFoo` in a function, in general we don't care so much
how that type is *defined*, we care that it has a correct `HasFFIType`
instance.[^6] For external types like `CFoo`, this would require listing the
`HasFFIType` instance in the external binding specification.

> [!WARNING]
>
> If an (external) type is used in a function binding and it is missing a
> `HasFFIType` instance, `hs-bindgen` will currently generate code that fails to
> compile. See [issue #2253][issue-2253].

However, having a `HasFFIType` instance is not the only ingredient we need for
generating a function binding. `hs-bindgen` tracks which instances a type has,
but it does not track the *implementation* of these instances.[^7] So even if
`hs-bindgen` knows that a type like `CFoo` has a `HasFFIType` instance, it does
not know what `FFIType CFoo` *is*. Still, `hs-bindgen` has to decide what FFI
type to use for `CFoo` in the `foreign import` declaration. So, `hs-bindgen`
uses the FFI type corresponding to the *underlying C type* of `CFoo`. Clearly,
`hs-bindgen` can also not check whether these two FFI types match after the
fact.

> [!WARNING]
>
> When using external types, the onus is on the user to ensure that its
> `HasFFIType` instance matches its underlying C type. `hs-bindgen` can not
> check whether these two FFI types match.

We can now generate a function binding for `g`, which looks roughly like so:

```hs
module OurLib where

import SomeOtherLib qualified

foreign import ccall safe "g" g_wrapper :: Int32 -> IO Int32

g :: SomeOtherLib.CFoo -> IO CInt
g = fromFFIType g_wrapper
```

## Portability
[t:portability]: #portability

While a *public* binding may look [portable][manual:portability], the
*implementation* of that binding is most probably not portable if it uses
`foreign import` declarations. To solve [the compositionality
problem][t:the-compositionality-problem], `hs-bindgen` [only uses FFI
types][t:the-hasffitype-class] in `foreign import` declarations. Which FFI types
are used (often) depends on the platform that bindings are generated on. Even if
using [cross-compilation][manual:cross-compilation], those FFI types will be
picked specifically for the platform that the bindings are generated for.

For example, if we have a C header that contains a function like this:

```c
int f(int, int);
```

Then `hs-bindgen` currently generates a *public* Haskell function binding with
the following type signature:

```hs
f :: CInt -> CInt -> IO CInt
```

The size of an `int` is platform-dependent, and `CInt`'s platform-dependent
definition reflects that size. As such, the *type* of `f` looks portable in the
sense that it can be used across multiple platforms (with different `int`
sizes).

Unfortunately, the *implementation* of `f` that `hs-bindgen` generates is *not*
portable. Assuming that the size of an `int` is 32 bits, the generated bindings
will look roughly like so:

```hs
foreign import ccall safe "f_wrapper" f_wrapper ::
     Int32 -> Int32 -> IO Int32

f :: CInt -> CInt -> IO CInt
f = fromFFIType f_wrapper
```

Notice that `f_wrapper` uses the FFI type `Int32` instead of `CInt`. `f_wrapper`
betrays the size of an `int`, whereas `f` abstracted away the `int` size by
using `CInt`. Using these bindings on platforms with other `int` sizes would be
unsafe.

> [!NOTE]
>
> For function bindings involving primitive C types like `int` (`CInt`), we
> might be able to generate portable bindings. See [issue #1747][issue-1747].

> [!WARNING]
>
> Portable types -- types that abstract away platform-dependent information --
> such as `CInt`, or even custom types that a user might define themselves, are
> currently not completely supported because FFI types break the abstraction
> boundary. We are planning on improving this. See [issue #1748][issue-1748].
