# FFI types

For a `foreign import` declaration to be valid its type must be a [*foreign
type*][haskell2010:ffi-foreign-types] or it will fail to compile. This depends
on the context of which modules are imported: `newtype`s[^1] are allowed, but its
constructor and *every constructor it depends on* must be in scope. `hs-bindgen`
guarantees that `foreign import`s compile by using *FFI types*.

[t:ffi-type-def]: #ffi-type-definition
<a id="ffi-type-definition">
> An FFI type is a Haskell type `F` paired with a Haskell module `M` that is known
to be legal in a `foreign import` as long as module `M` is imported.
</a>

Whenever a type `T` is intended to be used in a generated `foreign import`,
`hs-bindgen` will use that type's FFI type `F` there instead, and it will make
sure that the paired module `M` is imported. Additionally, `hs-bindgen` will
generate a *public function binding* that restores the original, more useful
type signature by converting function arguments to their FFI type, invoking the
`foreign import`, and converting the function result back from its FFI type. We
will show [Examples][t:examples] of what this looks like later.

To generate such bindings, `hs-bindgen` essentially needs to decide on three
pieces of information about a type such as `T`:

1. What is its FFI type `F`?
2. What module `M` needs to be imported?
3. How do we convert between `T` and `F`?

In general, `hs-bindgen` assigns FFI types to `newtype`s that it generates based
on *inheritance*. Whenever `hs-bindgen` generates a `newtype` `U` that wraps a
type `T`, then `U` inherits the FFI type `F` from `T`. Since `U` is a `newtype`
it is also straightforward to "lift" (e.g., `coerce`) the conversions between
`T` and `F` to conversions between `U` and `F`.

There are a number of "base" types in `HsBindgen.Runtime.Support` that map to
themselves as "base" FFI types[^2], such as `CInt` and `PtrVoid`. Without
external binding specifications[^3], any `newtype` that `hs-bindgen` generates
(transitively) wraps such a base type, and is therefore also assigned a base FFI
type, with straightforward conversion functions.

Alternatively, external binding specifications can be used to instruct
`hs-bindgen` to use external Haskell types instead of generating new bindings.
These external types may be generated by `hs-bindgen`, or they may implemented
by hand, in which case the implementer may have picked a custom FFI type (that
should satisfy all [necessary conditions][t:ffi-type-def]). Such
Haskell-side implementation details are recorded in external binding
specifications, because `hs-bindgen` can not detect this from just the C source
code. For example, an FFI type is recorded roughly as follows:

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example
ctypes:
- headers: example.h
  cname: T
  hsname: T
hstypes:
- hsname: T
  representation:
    newtype:
      ffitype:
        hsmodule: M
        hsname: F
```

Again, any `newtype` `U` that `hs-bindgen` generates that wraps such an external
type `T` will inherit `T`'s FFI type.

If the field is omitted from an external binding specification, then
`hs-bindgen` will default to assigning a "base" FFI type again based on `T`'s
*underlying C type*: the C type corresponding to `T` as reported by `libclang`.

> [!NOTE]
>
> It is not recommended to omit the `ffitype` field in external binding
> specifications, because the behaviour of assigning FFI types may be confusing
> in such cases.

Finally, `hs-bindgen` uses the `HasFFIType` run-time class to take care of the
conversions to and from FFI types in the generated bindings. Any Haskell type
`T` may be associated with an FFI type `F` by giving it an instance of the
`HasFFIType` class, including functions to convert from `T` to `F` and back.

```hs
class HasFFIType a where
  type FFIType a :: Type
  toFFIType :: a -> FFIType a
  fromFFIType :: FFIType a -> a
```

The class comes with default instances for "base" types that map to themselves
as "base" FFI types. `hs-bindgen` generates instances for `HasFFIType` whenever
applicable using `newtype`-deriving, which matches the inheritance-based
strategy of assigning FFI types. The `toFFIType` and `fromFFIType` functions are
used in the generated bindings.

> [!WARNING]
>
> If an external type is used in a function binding and it is missing a
> `HasFFIType` instance, `hs-bindgen` will currently generate code that fails to
> compile. See [issue #2253][issue-2253].

> [!WARNING]
>
> FFI types are currently not supported in prescriptive binding specifications.
> See [issue #2271][issue-2271].

## Examples
[t:examples]: #examples

In this subsection, we will use a series of examples to show how `hs-bindgen`
generates bindings that involve FFI types. We will use a running example of C
code in header `ffi-types/int.h`:

```c
typedef int A;
typedef A B;
extern void foo (B x);
```

There are two stacked `typedef`s `A` and `B`, and a function that uses `B` as
the type of its argument. The goal for each example is to obtain bindings for
`A`, `B`, and `foo`. Each example shows a slightly different use case.

The running example uses `typedef`s, but in general the example could use other
kinds of C type declarations as long as they translate to Haskell `newtype`s,
such as `enum`s and macro types; `newtype`s are the primary reason why FFI types
are necessary at all.

We will simplify and omit unnecessary details from Haskell code examples and
`yaml` file examples. We will also only look at the `*.Safe` modules, because
any generated bindings in the `*.Unsafe`, `*.FunPtr`, and `*.Global` modules
would work similary.

### Example 1
[t:example-1]: #example-1

In this example, we show how `hs-bindgen` generates bindings when no external
binding specifications are used at all. All bindings are generated in one go.

The bindings for types `A` and `B` go into module `Example1`:

```hs
module Example1 ( A(..), B(..) )

newtype A = A { unwrapA :: CInt }
  deriving newtype HasFFIType

newtype B = B { unwrapB :: A }
  deriving newtype HasFFIType
```

Both `A` and `B` are assigned `HsBindgen.Runtime.Support.CInt` as their FFI type
because they inherit it from `CInt`, which maps to itself as its FFI type.
Meaning that whenever we generate a `foreign import` declaration for a C
function that involves `A` or `B`, we would use `HsBindgen.Runtime.Support.CInt`
there instead.

The bindings for `foo` are put into module `Example1.Safe`:

```hs
module Example1.Safe ( foo ) where

import qualified Example1
import qualified HsBindgen.Runtime.Support

foreign import ccall safe "foo_wrapper" foo_wrapper ::
    HsBindgen.Runtime.Support.CInt -> IO ()

foo :: Example1.B -> IO ()
foo = \x0 -> foo_wrapper (toFFIType x0)
```

`foo` has a *public function binding* with a nice, useful type signature
involving `B`. The *implementation* does not use `B` however, it uses `B`'s FFI
type instead: `CInt`. `hs-bindgen` also makes sure to import
`HsBindgen.Runtime.Support`. `toFFIType` takes care of the conversion in the
body of `foo`.

### Example 2
[t:example-2]: #example-2

In this example, we show how `hs-bindgen` generates bindings when we only use
external binding specifications that are generated by `hs-bindgen` itself. The
goal is to generate bindings for `A`, `B`, and `foo` all in their own modules,
using default-generated external binding specifications as as inputs.

First, we generate bindings just for `A` and put them in module `Example2.A`:

```hs
module Example2.A ( A(..) )

newtype A = A { unwrapA :: CInt }
  deriving newtype HasFFIType
```

We also instruct `hs-bindgen` to generate an external binding specification for
this module:

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example2.A
ctypes:
- headers: ffi-types/int.h
  cname: A
  hsname: A
hstypes:
- hsname: A
  representation:
    newtype:
      ffitype:
        hsmodule: HsBindgen.Runtime.Support
        hsname: CInt
  instances:
  - HasFFIType
```

This specification lists that `A` has a `HasFFIType` class instance, and that
its FFI type is `HsBindgen.Runtime.Support.CInt`, same as in [Example
1][t:example-1].

Now, we generate bindings for `B` using `A`'s external binding specification as
input, and we put the bindings in module `Example2.B`:

```hs
module Example2.B ( B(..) )

import qualified Example2.A

newtype B { unwrapB :: Example2.A.A }
  deriving newtype HasFFIType
```

`hs-bindgen` can see in the external binding specification for `A` that it has a
`HasFFIType` instance, so we `newtype`-derive a `HasFFIType` instance again.
Moreover, `B` inherits its FFI type from `A`. We also instruct `hs-bindgen` to
generate an external binding specification for this module:

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example2.B
ctypes:
- headers: ffi-types/int.h
  cname: B
  hsname: B
hstypes:
- hsname: B
  representation:
    newtype:
      ffitype:
        hsmodule: HsBindgen.Runtime.Support
        hsname: CInt
  instances:
  - HasFFIType
```

Again, the binding specificiation lists that `B` has a `HasFFIType` class
instance and it lists `HsBindgen.Runtime.Support.CInt` as its FFI type, which it
inherited from `A`. It could only inherit this FFI type because the external
binding specification for `A` listed it.

Finally, we generate bindings for `foo` using `A` and `B`'s  external binding
specifications as inputs, and we put the bindings in module `Example2.C.Safe`.

```hs
module Example2.C.Safe ( foo ) where

import qualified Example2.B
import qualified HsBindgen.Runtime.Support

foreign import ccall safe "foo_wrapper" foo_wrapper ::
    HsBindgen.Runtime.Support.CInt -> IO ()

foo :: Example2.B.B -> IO ()
foo = \x0 -> foo_wrapper (toFFIType x0)
```

Like in [Example 1][t:example-1], it uses `B`'s FFI type in the `foreign
import`. It can only do this because the FFI type is specified in `B`'s external
binding specification.

### Example 3
[t:example-3]: #example-3

In this example, we show how `hs-bindgen` generates bindings when we use
external types that are implemented by hand. That means we use not only external
binding specifications that are generated by `hs-bindgen` itself, but also
external binding specifications that are written manually. In contrast to
[Example 2][t:example-2], we implement bindings for `A` by hand, but then we
follow the same process of generating bindings for `B` and `foo` in their own
modules, using `A` as an external type.

First, we manually implement bindings just for `A` and put them in module
`Example3.A`:

```hs
module Example3.A ( A(..), CInt(..) ) where

import Foreign.C.Types
import HsBindgen.Runtime.HasFFIType

newtype A = A CInt

instance HasFFIType A where
  type FFIType A = A
  toFFIType = id
  fromFFIType = id
```

Here we *choose* to map `A` to itself as its FFI type. Meaning that whenever we
generate a `foreign import` declaration for a C function that involves `A`, we
would use `Example3.A.A` there. Recall also the [definition of FFI
types][t:ffi-type-def], which prescribes that `A` is only an FFI type if it is
valid in a foreign import when `Example3.A` is imported. For this to be true, we
should also re-export `CInt` and its constructors.

We also write an external binding specification by hand:

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example3.A
ctypes:
- headers: ffi-types/int.h
  cname: A
  hsname: A
hstypes:
- hsname: A
  representation:
    newtype:
      ffitype:
        hsmodule: Example3.A
        hsname: A
  instances:
  - HasFFIType
```

This specifies the FFI type of `A`, and also that `A` has a `HasFFIType`
instance.

Now we generate bindings for `B` using `A`'s external binding specification as
input, and we put the bindings in module `Example3.B`:


```hs
module Example3.B ( B(..) )

import qualified Example3.A

newtype B { unwrapB :: Example3.A.A }
  deriving newtype HasFFIType
```

`hs-bindgen` can see in the external binding specification for `A` that it has a
`HasFFIType` instance, so we `newtype`-derive a `HasFFIType` instance again.
Moreover, `B` inherits its FFI type from `A`. We also instruct `hs-bindgen` to
generate an external binding specification for this module:

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example3.B
ctypes:
- headers: ffi-types/int.h
  cname: B
  hsname: B
hstypes:
- hsname: B
  representation:
    newtype:
      ffitype:
        hsmodule: Example3.A
        hsname: A
  instances:
  - HasFFIType
```

Again, the binding specificiation lists that `B` has a `HasFFIType` class
instance, but in contrast to [Example 2][t:example-2], it now lists
`Example3.A.A` as its FFI type, which it inherited from `A`. It could only
inherit this FFI type because the external binding specification for `A` listed
it.

Finally, we generate bindings for `foo` using `A` and `B`'s  external binding
specifications as inputs, and we put the bindings in module `Example3.C.Safe`.

```hs
module Example3.C.Safe ( foo ) where

import qualified Example3.A
import qualified Example3.B

foreign import ccall safe "foo_wrapper" foo_wrapper ::
    Example3.A.A -> IO ()

foo :: Example3.B.B -> IO ()
foo = \x0 -> foo_wrapper (toFFIType x0)
```

As always, it uses `B`'s FFI type in the `foreign import`. It can only do this
because the FFI types is specified in `B`'s external binding specification.

### Example 4

We could go even further than we did in [Example 3][t:example-3] and implement
`A` by hand as an abstract/opaque datatype. This is fine, as long as `A` maps to
a proper FFI type.

For example, we could come up with a internal representation for `A` that tracks
negative values, the zero value, and positive values in separate constructors.
We then assign `Foreign.C.Types.CInt` as its FFI type, with conversions between
`A` and `CInt`:

```hs
module Example4.A ( A, fromCInt ) where

import Foreign.C.Types

import HsBindgen.Runtime.HasFFIType

data A = Neg Word | Zero | Pos Word

fromCInt :: CInt -> A
fromCInt x
  | x < 0 = Neg (fromIntegral (abs x))
  | x == 0 = Zero
  | otherwise -- x > 0
  =  Pos (fromIntegral x)

toCInt :: A -> CInt
toCInt = \case
    Neg x -> - fromIntegral x
    Zero -> 0
    Pos x -> fromIntegral x

instance HasFFIType A where
  type FFIType A = CInt
  toFFIType = toCInt
  fromFFIType = fromCInt
```

The external binding specification we implement looks like so:

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example4.A
ctypes:
- headers: ffi-types/int.h
  cname: A
  hsname: A
hstypes:
- hsname: A
  representation:
    newtype:
      ffitype:
        hsmodule: Foreign.C.Types
        hsname: CInt
  instances:
  - HasFFIType
```

If we use `A`'s external binding specification as input to generating bindings
for `B` and `foo` like we did in [Example 3][t:example-3], then the outputs will
look the same save for the fact that `B`'s FFI type is now also
`Foreign.C.Types.CInt`.

## Standard library

The built-in external binding specificationfor the C standard library[^4]
assigns a lot of custom (i.e., *non-base*) FFI types. The rules of inheriting
FFI types apply the same way here as if it were any other external binding
specification. For example, if we have `typedef X` like so:

```c
#include <stddef.h>
typedef size_t X;
```

And `size_t` translates to `CSize` in the Haskell bindings which maps to itself
as its FFI type, then `X` will also map to `CSize` as its FFI type. Naturally,
if the built-in external binding specification were disabled, then we would
generate a new binding for `size_t` and map it to a base FFI type that `X` would
inherit.
