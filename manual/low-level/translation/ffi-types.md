# FFI types

For a `foreign import` declaration to be valid its type must be a [*foreign
type*][haskell2010:ffi-foreign-types] or it will fail to compile. This depends
on the context of which modules are imported: `newtype`s are allowed, but its
constructor and *every constructor it depends on* must be in scope. `hs-bindgen`
guarantees that `foreign import`s compile by using *FFI types*.

An FFI type is a Haskell type `F` paired with a Haskell module `M` that is known
to be legal in a `foreign import` as long as module `M` is imported. Whenever a
type `T` is intended to be used in a generated `foreign import`, `hs-bindgen`
will use that type's FFI type `F` there instead, and it will make sure that the
paired module `M` is imported. Additionally, `hs-bindgen` will generate a
*public function binding* that restores the original, more useful type signature
by converting function arguments to their FFI type, invoking the `foreign
import`, and converting the function result back from its FFI type. We will see
examples of what this looks like later in the [Examples][t:examples] subsection.

To generate such bindings, `hs-bindgen` essentially needs to decide on three
pieces of information about a type such as `T`:

1. What is its FFI type `F`?
2. What module `M` needs to be imported?
3. How do we convert between `T` and `F`?

The conversion in (3) is captured in a type class mechanism. Any Haskell type
`T` may be associated with an FFI type `F` by giving it ther proper instance of
the `HasFFIType` class, including functions to convert from `T` to `F` and back.

```hs
class HasFFIType a where
  type FFIType a :: Type
  toFFIType :: a -> FFIType a
  fromFFIType :: FFIType a -> a
```

These functions are invoked by the bindings to perform the conversion.
`hs-bindgen` also generates instances for `HasFFIType` whenever applicable, but
to do that it first needs to decide on (1) and (2).

Without using external binding specifications[^1], `hs-bindgen` will always assign
FFI types from a known set of "base" FFI types, such as `CInt`, `PtrVoid`. These
are all re-exported from `HsBdingen.Runtime.Support`.

Alternatively, external binding specifications can be used to instruct
`hs-bindgen` to use external Haskell types instead of generating new bindings.
These external types may be generated by `hs-bindgen`, or they may implemented
by hand, in which case the implementer may have picked a custom FFI type. Such
Haskell-side implementation details can not be detected from the C source code
itself by `hs-bindgen`, so instead the FFI type and paired module are recorded
in an external binding spec for `hs-bindgen` to rely on.

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example
ctypes:
- headers: example.h
  cname: T
  hsname: T
hstypes:
- hsname: T
  representation:
    newtype:
      ffitype:
        hsmodule: M
        hsname: F
  instances:
  - HasFFIType
```

> [!WARNING]
>
> If an (external) type is used in a function binding and it is missing a
> `HasFFIType` instance, `hs-bindgen` will currently generate code that fails to
> compile. See [issue #2253][issue-2253].

> [!WARNING]
>
> `ffitype` is currently not supported in prescriptive binding specifications.
> See [issue TODO][?].

> [!WARNING]
>
> When using external types, the onus is on the user to ensure that its
> `HasFFIType` instance matches its underlying C type. `hs-bindgen` can not
> check whether these two FFI types match.

## Examples
[t:examples]: #examples

In this subsection, we will show we will use a series of examples to show how
`hs-bindgen` generates bindings that involve FFI types. We will use a running
example of C code that looks roughly like so:

```c
typedef ... A;

typedef A B;

extern void foo (B x);
```

There are two stacked `typedef`s[^10] `A` and `B`, and a function that uses `B` as
the type of its argument. The implementation of `A` may vary depending on the
example.

[^10]: The running example uses `typedef`s, but in general the example could
use other kinds of `C` type declarations as long as they translate to Haskell
`newtype`s, such as `enum`s and macro types. `newtype`s are the primary reason
why FFI types are necessary at all.

The goal for each example is to obtain bindings for `A`, `B`, and `foo`,
separated into different modules for each. Primarily this is achieved using
external binding specifications, but each example aims to show a slightly
different use case.

## Example 1

In this example, we show how `hs-bindgen` generates bindings when we only use
external binding specifications that are generated by `hs-bindgen` itself. This
is a good starting point to show `hs-bindgen`'s *default* behaviour, i.e., when
users do not instruct `hs-bindgen` to use types that they manually implemented.

For this example, we will generate bindings for header `int.h`, which defines
`typedef` `A` as an `int`:

```c
typedef int A;
typedef A B;
extern void foo (B x);
```

The goal is to generate bindings for `A`, `B`, and `foo` all in their own
modules, using default-generated external binding specifications as as inputs.

First, we generate bindings just for `A` and put them in module `Example1.A`,
which looks roughly like so:

```hs
module Example1.A ( Example1.A.A(..) )

newtype A = A { unwrapA :: CInt }
  deriving newtype HasFFIType
```

We `newtype`-derive a `HasFFIType` instance for `A`, which looks roughly like
so:

```hs
instance HasFFIType A where
  FFIType A = FFIType CInt -- FFIType CInt ~ CInt
  toFFIType (A x) = toFFIType x -- toFFIType x ~ x
  fromFFIType x = A (fromFFIType x) -- fromFFIType x ~ x
```

From this instance, we can see that `A` maps down to `CInt`. Meaning that
whenever we generate a `foreign import` declaration for a C function that
involves `A`, we would use `CInt` there instead.

We also instruct `hs-bindgen` to generate an external binding specification for
this module, which looks roughly like so:

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example1.A
ctypes:
- headers: ffi-types/int.h
  cname: A
  hsname: A
hstypes:
- hsname: A
  representation:
    newtype:
      ffitype:
        hsmodule: HsBindgen.Runtime.Support
        hsname: CInt
  instances:
  - HasFFIType
```

Not only does this specify that `A` has a `HasFFIType` class instance, it also
encodes the concrete FFI type in the `ffitype` field.

Now, we generate bindings for `B` using `A`'s external binding specification as
input, and we put the bindings in module `Example1.B`, which looks roughly like
so:

```hs
module Example2.B ( Example2.B.A(..) )

import qualified Example1.A

newtype B { unwrapB :: Example1.A.A }
  deriving newtype HasFFIType
```

`hs-bindgen` can see in the external binding specification for `A` that it has a
`HasFFIType` instance, so we `newtype`-derive a `HasFFIType` instance again,
which maps `FFIType B` down to `FFIType A`, and then down to `CInt` again.

We also instruct `hs-bindgen` to generate an external binding specification for
this module, which looks roughly like so:

```yaml
version:
  hs_bindgen: 0.1.0
  binding_specification: '1.0'
hsmodule: Example1.B
ctypes:
- headers: ffi-types/int.h
  cname: B
  hsname: B
hstypes:
- hsname: B
  representation:
    newtype:
      ffitype:
        hsmodule: HsBindgen.Runtime.Support
        hsname: CInt
  instances:
  - HasFFIType
```

Not only does this specify that `B` has a `HasFFIType` class instance, it also
encodes the *same* FFI type in the `ffitype` field as `A` did. It could only
repeat the `ffitype` here because it was also listed in the external binding
specification for `A`. If it were omitted,

Finally, we generate bindings for `foo` using `A` and `B`'s  external binding
specifications as inputs, and we put the bindings in module `Example1.C.Safe`.[^11]

[^10]: This step also generates other modules such as `Example1.C.Unsafe` and
    `Example1.C.FunPtr`, but we won't need to look at them.

```hs
module Example1.C.Safe ( Example1.C.Safe.foo ) where

import qualified Example1.B
import qualified HsBindgen.Runtime.Support

foreign import ccall safe "foo_wrapper" foo_wrapper ::
    HsBindgen.Runtime.Support.CInt -> IO ()

foo :: Example1.B.B -> IO ()
foo = \x0 -> foo_wrapper (toFFIType x0)
```

`foo` has a *public function binding* with a nice, useful type signature
involving `B`. The *implementation* does not use `B` however, it uses `B`'s FFI
type instead. It knows to import `HsBindgen.Runtime.Support` and use
`HsBindgen.Runtime.Support.CInt` in the `foreign import` only because it is
specified in `B`'s external binding spec.
