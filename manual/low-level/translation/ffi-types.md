# FFI types

A `HasFFIType` instance declaration for a type `T`, mapping `FFIType T` to
`M.T'`, is valid if `T'` is legal to appear in `foreign import` declarations in
context where `M` is in scope.

Compositionality of generated bindings is achieved through the use of [external
binding specifications][manual:binding-specifications]. They allow generated
bindings to use *external types* imported from other modules. These external
types may be generated by `hs-bindgen` itself, or they may be implemented by
hand. When these external types are used in FFI that involves `foreign import`
declarations, we have to be sure that the `foreign import` has a valid [foreign
type][haskell2010:ffi-foreign-types], or it will fail to compile. It is hard to
guarantee this *in general* without additional infrastructure to guide binding
generation. Manually implemented

Due to an unfortunate quirk of how `foreign import` declarations involving
newtypes may not compile *in general*, `hs-bindgen` generates `foreign import`s
with *FFI types* only. An FFI type is a `hs-bindgen` concept: it is used as a
stand-in for the original type in a `foreign import` declaration, and ensures
that the `foreign import` compiles. All types that are intended to be used in
FFI that involves `foreign import`s should be assigned an FFI type. When
`hs-bindgen` generates types, it will assign FFI types to them whenever
applicable.



> Given any number of external types as inputs to binding generation, assuming
> that they have proper FFI types, `hs-bindgen` will generate:
>
> * New types with proper FFI types.
> * `foreign import` declarations that compile.





This manual section illustrates why we need FFI types, and how what users should
watch out for regard when writing external types by hand.

## The compositionality problem

Let's start with an example. Suppose we have a C header `our_lib.h` with a
function `g` that we want to generate bindings for. `g` uses a type `Foo` from
another library `some_other_lib.h`:

```c
// some_other_lib.h
typedef int Foo;

// our_lib.h
#include <some_other_lib.h>
int g(Foo x);
```

We have an external binding specification that maps `Foo` to some type `CFoo` in
some Haskell library somewhere. Naively, `hs-bindgen` could generate something
like so:

```hs
module OurLib where

import SomeOtherLib qualified

foreign import ccall safe "g" g :: SomeOtherLib.CFoo -> IO CInt
```

However, `g` may fail to compile depending on how `CFoo` is implemented.

For `ghc` to compile `g`, it must be able to determine whether the type of `g`
is a valid *foreign type*. Foreign types are defined in [Section 8.4.2 of the
Haskell 2010 Language Report][haskell2010:ffi-foreign-types].[^1] Broadly,
foreign types are function types that (may) end in `IO`, where each argument and
result type is a marshallable type such as `Int`, `Word64`, or `Ptr a`. `data`
types are never allowed, but `newtype`s are allowed as long as `ghc` can
determine that they are `Coercible` to a valid foreign type.[^2]

Going back to the example, in order to determine whether a newtype `CFoo` is a
foreign type, the constructor for `CFoo` *and the constructors for anything
`CFoo` depends on itself* must be in scope. In other words, `CFoo` should be
*transparent* all the way down. This is the source of what we call the
*compositionality problem*: it is hard to ensure *in general* that a newtype
`CFoo` is transparent when generating bindings.

Let's say `CFoo` is defined as follows:

```hs
newtype CFoo = CFoo CInt
```

In this case, `CFoo` is valid foreign type. Importing `SomeOtherLib` brings the
constructor for `CFoo` in scope, and `CInt` is a valid foreign type as long as
its constructor is imported -- which is always true for generated bindings.[^3]

Now let's say that `CFoo` is defined as follows instead:

```hs
newtype CFoo = CFoo CBar
```

Assuming `CBar` is defined in some other module, `g` no longer compiles unless
we somehow also import the module that defines `CBar`, even though `CBar` could
be an implementation detail of `CFoo`.

We could insist that if you have a type intended for use in FFI like this, you
must also re-export the constructors for everything that the type depends on.
Unfortunately, that does not work if there are name clashes. Haskell does not
allow exporting multiple *different* types with the same name from the same
module -- not even if the types have a unique qualified name. For example:

```hs
newtype CFoo = CFoo SomeInternalModule.CFoo
```

Alternatively, we could insist that all necessary constructors must be imported.
To achieve this, we would have to list "additional required imports" in the
external binding specification format. Though this would work, it would be
messy. An external binding specification for a module in one Haskell package
might refer to *other* packages. As a result, users would have to declare more
packages in their cabal `build-depends` field. And in Template Haskell mode,
`hs-bindgen` cannot generate additional imports, so users would have to add
those by hand.

## Solution

The actual solution that `hs-bindgen` uses is this: all types intended for use
in `foreign import` declarations, including external types like `CFoo`, should
be associated with an *FFI type* which is used in `foreign import` declarations
instead of the original type. These FFI types should always be accepted by `ghc`
as valid foreign types. By default, `hs-bindgen` will always generate types with
associated FFI types that satisfy that property.[^6] Since external types may also
be implemented by hand, it is in that case the user's responsibility to assign a
proper FFI type.

> [!IMPORTANT]
>
> If a user implements an external type by hand, then it is the user's
> responsility that the external type is associated with a proper FFI type.


We have a class `HasFFIType` in `hs-bindgen-runtime`, which maps any type to its
FFI type, along with conversions. The class comes with a number of default
instances for types from `base`, which for the most part are the identity
mapping. The class roughly looks like this:

```hs
class HasFFIType a where
  type FFIType a :: Type
  toFFIType :: a -> FFIType a
  fromFFIType :: FFIType a -> a
```

Even if `hs-bindgen` uses FFI types in the *implementation* of function
bindings, `hs-bindgen` will still generate a *public function binding* -- a
separate Haskell function -- with more useful non-FFI types. Using the
`HasFFIType` class, the public function bindings converts the function arguments
to their FFI types before invoking the `foreign import` declaration, and the
function result is mapped from its FFI type back to its actual type.

Now, if we want to use `CFoo` in a function, in general we don't care so much
how that type is *defined*, we care that it has a correct `HasFFIType`
instance.[^4]

> [!WARNING]
>
> If an (external) type is used in a function binding and it is missing a
> `HasFFIType` instance, `hs-bindgen` will currently generate code that fails to
> compile. See [issue #2253][issue-2253].





Let's go back to the `CFoo` example from the previous sub-section.

The `HasFFIType` instance for `CFoo = CFoo CInt` may look like so if it were
generated by `hs-bindgen`:

```hs
instance HasFFIType CFoo where
  type FFIType CFoo = FFIType CInt
  toFFIType (CFoo x) = toFFIType x
  fromFFIType x = CFoo (fromFFIType x)
```

`HasFFIType` instances are composable, meaning that the `HasFFIType` instance
for `CFoo` can defer to the the `HasFFIType` instance for `CInt`.

We can now generate a function binding for `g`, which looks roughly like so:

```hs
module OurLib where

import SomeOtherLib qualified

foreign import ccall safe "g" g_wrapper :: CInt -> IO CInt

g :: SomeOtherLib.CFoo -> IO CInt
g = \x -> fromFFIType <$> g_wrapper (toFFIType x)
```


The FFI type may be imported
from the same module as the external type, or from some other specified module,
and a type may even assign itself as its FFI type if it is a valid foreign type.

However, having a `HasFFIType` instance is not the only ingredient we need for
generating a function binding. `hs-bindgen` tracks which instances a type has,
but it does not track the *implementation* of these instances.[^5] So even if
`hs-bindgen` knows that a type like `CFoo` has a `HasFFIType` instance, it does
not know what `FFIType CFoo` *is*. Still, `hs-bindgen` has to decide what FFI
type to use for `CFoo` in the `foreign import` declaration. So, `hs-bindgen`
uses the FFI type corresponding to the *underlying C type* of `CFoo`. Clearly,
`hs-bindgen` can also not check whether these two FFI types match after the
fact.

> [!WARNING]
>
> When using external types, the onus is on the user to ensure that its
> `HasFFIType` instance matches its underlying C type. `hs-bindgen` can not
> check whether these two FFI types match.
