# Managing Dependencies

`hs-bindgen` gets its dependencies from two places, and Cabal and Nix read
different files to find them. This document describes the version pins and how
to change them.

## Version pins

| Dependency | Cabal reads | Nix reads |
|---|---|---|
| Hackage package | `index-state` in `cabal.project.base` | `nix/generated/<package>.nix` |
| Git revision | `source-repository-package` in `cabal.project.base` | `nix/generated/<package>.nix` |
| Package in this repo | `packages` in `cabal.project` | `nix/generated/<package>.nix` |

`cabal.project.base` is the single source of truth: every other project file in
the repository imports it, directly or transitively, including the ones under
`manual/` and `examples/`.

The expressions under `nix/generated/` are a mirror of that source of truth,
generated by [`nix/generate.sh`](../nix/generate.sh) using `cabal2nix`. They are
checked in, and each one is self-contained: `src` is a `fetchgit` for a git
revision, a Hackage tarball for a Hackage package, and the in-repo directory for
our own packages.

The mirror does not update itself. `scripts/ci/check-nix-pins.sh` (run by the
"Check filesystem" workflow) fails if a git pin and its generated expression
disagree.

## Bumping a git-pinned dependency

Most external packages come from Hackage. A package is pinned to a git
revision only while `hs-bindgen` needs an unreleased change from it; the pin
should be removed once that change is published.

```bash
# Bump to the remote HEAD.
./scripts/update-git-dependency.sh libclang-bindings

# Or bump to a specific revision.
./scripts/update-git-dependency.sh --revision REV libclang-bindings
```

The script rewrites the stanza's `tag` and regenerates the affected expressions
under `nix/generated/`. Commit `cabal.project.base` and `nix/generated/`
together.

A stanza with several `subdir`s provides several packages that share one `tag`,
so bumping any one of them bumps all of them; the script regenerates all of
their expressions.

Note that a git revision usually keeps the version number of the release it
follows, so a stale pin may claim the same version while referring to different
code. The consistency check checks the pins match exactly.

## Adding or removing a git pin

Edit the `source-repository-package` stanzas in `cabal.project.base` by hand,
then regenerate:

```bash
./nix/generate.sh <package>    # or without arguments, to regenerate everything
```

When *removing* a stanza, the package falls back to Hackage, so it also needs an
entry in the `HACKAGE_PACKAGES` list in `nix/generate.sh` (with the version that
`index-state` resolves to) before regenerating.

## Bumping the Hackage index-state

Change `index-state` in `cabal.project.base`, then revisit the pinned versions
in the `HACKAGE_PACKAGES` list in `nix/generate.sh` and regenerate. Those
versions are pinned deliberately: `cabal2nix` resolves an unpinned package to
whatever is newest on Hackage, which has nothing to do with our `index-state`,
so leaving them unpinned would make regeneration non-reproducible.

## Requirements

`nix/generate.sh` needs Nix (it runs `cabal2nix` from `nixpkgs`) and network
access. `scripts/ci/check-nix-pins.sh` needs neither.

## Notes

While generating a git expression, `cabal2nix` prints alarming-looking noise
("*** parsing cabal file: ...: Not a directory", "error: failed to open
archive"): it probes two `nix-prefetch-url` fetchers that cannot work on a git
URL before falling back to `nix-prefetch-git`. This is harmless as long as the
script exits successfully.
