# Known Issues

> Current version: 0.1.0.

Whenever we release `hs-bindgen`, our goal is of course to release a product
without any known bugs. However, this is not always practical: some bugs have so
little impact that holding up a release until they are fixed would be
counterproductive. We list these known issues in this file.

Some notes on the provenance of this file:

* This does not replace the [issue tracker][issue-tracker]: bugs should be
  reported and discussed there.
* This file is `hs-bindgen` version specific: it is bundled with every Hackage
  release, and the version number is confirmed at the top of the file. Only bugs
  that are present in the stated version are listed.
* This file exists to make it possible for users to quickly scan through the
  list of known issues to see if any are relevant to them. It is _not_ intended
  to be the authoritative description of these problems; link to specific issues
  on the issue tracker instead.

## Literate mode fails to detect changes in dependent C files

> https://github.com/well-typed/hs-bindgen/issues/1583

When using `hs-bindgen` in literate mode, bindings won't be re-generated when
the C headers have changed.

## Some parse failures are not printed

> https://github.com/well-typed/hs-bindgen/issues/1851

Trace messages for unnamed declarations that cannot be selected are lost in some
cases.  In the following example, the reason that the declarations cannot be
selected (`long double` is not supported) is not shown.

```c
struct foo {
  struct {
     long double not_supported;
  } field;
};
```

## Generated bindings for undef-ed macros fail to compile

> https://github.com/well-typed/hs-bindgen/issues/1956

Bindings for a declaration that uses a macro that is later undefined still
use the macro and therefore fail to compile.  Example:

```c
#define T int
void foo (T x);
#undef T
```

## Missing type class instances can result in invalid generated code

> https://github.com/well-typed/hs-bindgen/issues/2253

The code generated by bindgen can depend on the existence of certain type class
instances; those instances are normally also generated by `hs-bindgen`, but
sometimes we cannot, either because the types are external (declared through an
external binding spec), or because the corresponding C types are opaque. When
this happens, `hs-bindgen` might generate code that fails to compile.

## Return-by-value of struct-of-const results in invalid code

> https://github.com/well-typed/hs-bindgen/issues/1515

We generate invalid code for functions that return a struct _by value_ where
that struct has _const_ fields:

```c
struct S { const int x; int y; };
struct S f1();
```

## Return-by-value of const-struct results in invalid code

> https://github.com/well-typed/hs-bindgen/issues/1514

Related to #1515, but even more obscure: we generate code for funcitons that
return a struct _by value_ which it _itself_ marked `const`:

```c
struct S { int x; };
const struct S f1();
```

Note that this `const` qualifier here is anyway pointless.

## "Invisible" structs result in invalid code

> https://github.com/well-typed/hs-bindgen/issues/1228

When a function declaration contains a struct declaration, such as

```c
void f1(struct named_struct { int x; int y; } arg);
```

we generate invalid code. Note that this is only barely valid C, `clang` will
issue a warning "declaration of 'struct named_struct' will not be visible
outside of this function".
